# Turn real mocap into believable hub workers

Workers in a synthetic scene look like zombies for three fixable reasons, not because the source motion is bad. First, the retarget copies local bone rotations between two rigs whose rest poses differ, so the arms end up hanging wrong. Second, hip translation is not scaled to the avatar's leg length, so the feet slide and the hips sink. Third, every worker's cycle runs in lockstep. The fix is a deterministic, numpy-first pipeline you write yourself and run inside `blender -b`. It has six stages. (1) Pose both rigs into the same T-pose and copy **world-space** rotation changes, not local channels. (2) Scale root motion by the leg-length ratio. (3) Cut AndyData's labelled takes into reach/pick/carry/place clips with event tags. (4) Join clips with inertialization, then fix feet and hands with small, ramped two-bone IK corrections. (5) Fit each station to real hub numbers: about 2–3 s per inducted parcel, 15–18 lifts/min when unloading a trailer, roll-cage handles at about 1 m. (6) Give every worker a desynchronised, weighted-random task schedule. Perception research backs the priority order: viewers detect foot sliding below about 21 mm, and as few as three desynchronised motions pass as a fully varied crowd. That makes timing, desync and foot contact worth more than a bigger clip library. Licences are mostly clean. Rocketbox is MIT, and AndyData and 100STYLE are CC BY 4.0. The traps are LaFAN1, Bandai Namco and Holden's Geno rig (all non-commercial), Mixamo (proprietary terms), and the FreeMoCap add-on (AGPL, so it may only run offline as a tool). The manual-material-handling set was never located, so it stays excluded until its licence is checked.

## Matching rest poses in world space removes zombie arms

The core idea: two skeletons can only share motion if you first agree on what "neutral" means. If you copy local rotations from a BVH rig onto a rig with a different rest pose, the BVH corrupts the target "due to differences in rest poses". Diffeomorphic's fix is to "copy the rotation in world space rather than in the local space of each bone". At frame zero, both armatures are put into a reference T-pose "obtained by bending but not twisting the limbs". The per-bone world-rotation difference measured there then corrects every other frame ([Diffeomorphic: how it works](https://diffeomorphic.blogspot.com/p/bvh-how-it-works.html)). This matters a lot for Rocketbox. Microsoft's own Unity importer had to "set the avatars into T-pose and reorganize the bones" ([Microsoft-Rocketbox](https://github.com/microsoft/Microsoft-Rocketbox)), so the shipped 3ds Max bind pose is not a usable reference. Feed an A-pose target with T-pose source data and the arms sit tens of degrees off on every frame. That is the classic zombie-arm look.

Do the maths yourself in about 200 lines rather than relying on UI-driven add-ons. The `nla.bake` operator wants a UI context, which is awkward headless, and add-on operators under `temp_override` are unverified in background mode. For each mapped bone pair, store the offset `Off_b = Rs_ref⁻¹ · Rt_ref` at the shared T-pose, using full world matrices (`obj.matrix_world @ pose_bone.matrix`). That way, BVH axis conventions and FBX's centimetre scale and −90° X rotation get folded in automatically. Then on each frame set `Rt = Rs · Off_b`, convert to local with `obj.convert_space(..., from_space='POSE', to_space='LOCAL')`, and walk the chain from root to leaves. Because you never touch local channels, the Biped habit of running bones along local +X (Blender expects +Y) stops mattering. Pose Rocketbox into T-pose with a swing-only rotation per limb (`Vector.rotation_difference` between the bone direction and the T-pose direction). That is exactly the "bend not twist" rule. These details are standard maths, not taken from a Rocketbox-specific source, because no Microsoft or community guide on BVH-to-Rocketbox retargeting in Blender was found.

Root motion needs its own rule. Put world translation and heading on `Bip01`, and pelvis tilt on `Bip01 Pelvis` (the source "Hips"). Never put translation on both, or you get double offsets. Scale translation as `p_t = p_t_ref + (p_s − p_s_ref) · (L_t / L_s)`, where L is the hip-to-ankle length in each reference pose. Unscaled translation gives the wrong stride, so the feet slide. Apply the FBX scale before you measure L, or the ratio is off by 100×. The bone names (`Bip01 L UpperArm`, `Bip01 L Finger0`, possible `ForeTwist` bones), the unit scale and the bind-pose arm angle all come from Biped convention and are not verified on these files. Dump `armature.data.bones` from one Rocketbox FBX before writing the name map, and build one name map per dataset. Xsens BVH in AndyData and 100STYLE's renamed joints (Chest, Collar, Shoulder) differ ([100STYLE](https://www.ianxmason.com/100style/)). None of the sources have finger data, as Holden notes for 100STYLE ([100style-retarget](https://github.com/orangeduck/100style-retarget)). So set a relaxed static hand pose instead of leaving the stiff bind pose, and spread forearm twist across any twist bones so wrists don't "candy-wrap".

Each source needs its own preparation. 100STYLE takes "begin and end with T-poses". Trim them with `Frame_Cuts.csv`, but first take those T-pose frames as your retarget reference ([100STYLE](https://www.ianxmason.com/100style/)). AndyData already ships BVH, so download only the 1.8 GB `xsens_bvh.zip`, not the 41 GB MVN archive ([Zenodo 3254403](https://zenodo.org/records/3254403)). For your own phone footage, the FreeMoCap add-on builds a rig whose rest pose is a T-pose "makes retargeting easier". It recommends starting each take with a few seconds of standing still, feet flat ([FreeMoCap add-on](https://github.com/freemocap/ajc27_freemocap_blender_addon)). That still window doubles as your ground-height calibration. The add-on is AGPL and its documented workflow is GUI-only. Run it in a separate offline step, export the armature with Blender's built-in BVH exporter, and retarget from that file. Phone data is noisy, especially in depth. Clean it in this order: snap bone lengths to their median, then filter joint positions, then compute rotations. Smoothing rotations afterwards is weaker. The 1€ filter is the standard speed-adaptive choice. Tune it by setting beta to 0 with a mincutoff near 1 Hz to kill jitter while still, then raise beta in ×10 steps from about 0.001 while moving fast to cut lag ([1€ Filter](https://gery.casiez.net/1euro/)). Offline, a zero-lag Savitzky–Golay filter from BSD-licensed scipy also works. A window of about 9–15 frames at 30 fps is a starting value, not a sourced one.

Blender 5 breaks older scripts in one important way. **`Action.fcurves` was a deprecated proxy slated for removal in 5.0**, and keys now go through slotted actions and channelbags ([4.4 slotted actions notes](https://developer.blender.org/docs/release_notes/4.4/upgrading/slotted_actions/); [5.0 API](https://docs.blender.org/api/5.0/bpy.types.ActionChannelbagFCurves.html)). Bone visibility and selection also moved to pose bones in 5.0 ([5.0 animation notes](https://developer.blender.org/docs/release_notes/5.0/animation_rigging/)). Write keys in bulk. This beats calling `keyframe_insert` per frame and also avoids `nla.bake`:

```python
act  = bpy.data.actions.new("worker_07")
slot = act.slots.new(id_type='OBJECT', name="worker_07")
strip = act.layers.new("base").strips.new(type='KEYFRAME')
cb = strip.channelbag(slot, ensure=True)
for i in range(4):  # quaternion w,x,y,z
    fc = cb.fcurves.new('pose.bones["Bip01 Pelvis"].rotation_quaternion', index=i)
    fc.keyframe_points.add(n_frames)
    fc.keyframe_points.foreach_set("co", np.c_[frames, q[:, i]].ravel())
ob.animation_data_create(); ob.animation_data.action = act; ob.animation_data.action_slot = slot
```

Check the exact signatures against the 5.0 API docs. Write `rotation_quaternion` rather than Euler channels, and enforce hemisphere continuity first (`if q_t·q_{t-1} < 0: q_t = −q_t`). Interpolating between flipped quaternions causes the 360° wrist and spine spins that make a worker look possessed.

## Edit clips in a fixed order: cut, retime, warp, blend, then pin

Once motion lives on the Rocketbox skeleton as arrays, the editing stack turns generic bench-task mocap into parcel handling. The order matters because each stage breaks something the next one repairs.

**Cut on labels, not by hand.** AndyData's label CSV supports run-length encoding of the action column into intervals ([Zenodo 3254403](https://zenodo.org/records/3254403)). Snap each boundary to the nearest wrist-speed minimum within about ±0.15 s and pad clips by 0.3–0.5 s so the blends have material to work with. Store a JSON sidecar per clip with `grasp_frame`, `release_frame`, foot-contact intervals, root heading and hand position relative to the pelvis. The glove-pressure stream can confirm grasp and release frames. The windows and padding here are engineering starting values, and the exact label names still need checking against the CSV.

**Retime with anchored, monotone warps.** Map source event frames to the times the scene requires (the clip start, the moment the parcel arrives on the belt, the release) with a monotone cubic such as scipy's `PchipInterpolator`. This is Kovar and Gleicher's timewarp idea, a "strictly increasing function that returns sets of corresponding frames" ([Registration Curves](https://research.cs.wisc.edu/graphics/Gallery/kovar.vol/RegistrationCurves)). Keep the local speed ratio near 1 during foot plants and the grasp, and push the stretch into reach and transport phases. Production crowd tools cap random speed changes at around 0.8–1.2× and warn that large ratios look unrealistic on walks ([Golaem](https://help.autodesk.com/cloudhelp/ENU/GOLAEM-Maya/files/tutorials/animation-0/glm_adding-variety-your-characters-animation.html)). If the scene needs more time than that allows, insert a short idle or hold rather than slowing the motion into floatiness. Slerp quaternions at fractional source frames. Save DTW (Apache-licensed dtaidistance, with a `window` band ([dtaidistance](https://github.com/wannesm/dtaidistance))) for aligning two takes with each other, such as moving event tags from a labelled clip to your own unlabelled phone take.

**Warp space with displacement curves.** Witkin and Popović's motion warping derives a smooth deformation from a few keyframe-like constraints while keeping the original's "fine structure" ([CMU RI](https://www.ri.cmu.edu/publications/motion-warping)). Unreal's Skew Warp applies the same idea to root motion inside a notify window, so the character reaches a named target by the end of the window ([UE Motion Warping](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-warping-in-unreal-engine)). In practice, compute the difference between the clip's hand position at `grasp_frame` and the real parcel grip point. Then add that delta to `Bip01` with a smoothstep weight rising from 0 to 1 over the window before the grasp. Put the offset where the source root is already moving (a step-in or a turn), not where the actor stands still, or you create the sliding you are trying to avoid. As starting values: let IK alone absorb up to roughly 5–8 cm, use a root warp for roughly 8–30 cm, and pick a different clip beyond that (a deep squat for floor-level parcels, an overhead reach for the top of a trailer wall). Keep yaw changes under about 30–45° per window. These magnitudes are practitioner rules of thumb, not measured limits. After any root warp, re-pin every foot that is in contact. Kovar's footskate cleanup moves the root to where the ankle can reach, then solves the limb, then stretches the leg slightly for any residual ([Footskate Cleanup](https://research.cs.wisc.edu/graphics/Gallery/kovar.vol/Cleanup)).

**Join clips with inertialization, not crossfades.** A crossfade averages two motions whose feet are in different places, so the blended foot slides by construction. Inertialization cuts straight to the destination clip and adds a decaying offset. Bollo's Gears of War 4 method records "the source animation's velocity and the difference between the source and target poses", then lets that difference die away ([Bollo 2017](https://history.siggraph.org/wp-content/uploads/2022/09/2017-Talks-Bollo_High-Performance-Animation-in-Gears-of-War-4.pdf)). Holden's critically damped spring version fits in a few lines: on transition `off_x = (src_x + off_x) − dst_x`, then decay with `decay_spring_damper_exact` each frame. The spring "can easily overshoot" but "tends to look smooth" ([Spring Roll Call](https://theorangeduck.com/page/spring-roll-call)). Dead blending is the backup. It extrapolates the source and smoothsteps into the destination, with about **0.2 s as a normal blend time and 1 s "unrealistically long"** ([Dead Blending](https://theorangeduck.com/page/dead-blending)). Pick the switch frame by searching the overlapping ~0.3 s of each clip for the closest pose and velocity after aligning the roots on the floor plane. Registration curves show why that alignment matters: averaging roots of differently curving motions makes characters "slide and flip" ([Registration Curves](https://research.cs.wisc.edu/graphics/Gallery/kovar.vol/RegistrationCurves)). Full motion matching is unnecessary here. A scripted clip graph with best-switch-frame search is more controllable for a handful of known actions.

**Pin contacts with small, ramped two-bone IK.** Treat IK as a correction that rides on top of the mocap, not a replacement for it. Detect foot contacts by height (about 2–5 cm) and speed (about 10–20 cm/s) with hysteresis and a minimum length of 4–6 frames. Lock each contact to its first-frame world position, solve Thigh–Calf–Foot analytically, and blend in and out. Holden's demo enters and exits locks by inertialization and unlocks when the lock drifts past an `unlock_radius` ([Code vs Data Driven Displacement](https://theorangeduck.com/page/code-vs-data-driven-displacement)). For hands, animate the IK target as `mocap_hand + w(t)·(grip − mocap_hand_at_grasp)` with w ramping over about 0.2–0.4 s before the grasp. Take the pole from the mocap's own elbow direction each frame so the arm bends the way the actor's did. Unity's Two Bone IK exposes the same separate weight, hint and target-offset controls ([Unity TwoBoneIK](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/TwoBoneIKConstraint.html)). If the residual exceeds about 8–10 cm, increase the root warp instead, or the elbows lock straight and the shoulders hunch. A perception detail sharpens this choice. When viewers compared cleanup methods, **simple limb lengthening was preferred over IK plus trajectory smoothing** ([Pražák et al. 2011](https://diglib.eg.org/items/74844741-a900-4f91-886f-b89bf331cf98/full)). So allow a few millimetres of leg stretch for the last residual, rather than forcing a stiff knee. For parcels, bake the world matrix every frame: world-keyed on the belt before the grasp (moving at belt speed, so the grip target moves too), `hand_world · offset` while carried, and back to world on release. Baking avoids headless "Child Of set inverse" pitfalls. Writing two-bone IK in numpy (law of cosines plus aim) also avoids Blender's need for a per-rig `pole_angle`. The IK property names cited for Blender's constraint could not be checked against the 5.0 docs.

**Protect the weight cues.** Heaviness lives in the actor's preparatory dip, slower lift onset and pelvis drop. Smooth warps keep that "fine structure" ([CMU RI](https://www.ri.cmu.edu/publications/motion-warping)), while blends can turn destination detail "mushy" ([Dead Blending](https://theorangeduck.com/page/dead-blending)). Keep transitions out of the ~0.3 s before lift-off and after set-down, hold the time-warp ratio near 1 through the loaded lift, and pick AndyData clips whose EAWS posture labels match the load. An optional effort layer of 1–3 cm pelvis drop just after the grasp can add mass. For roll cages, let the cage lag the body by 0.1–0.2 s at start-up. These are engineering suggestions; no study on perceived weight was retrieved.

## Real hub numbers set each station's rhythm and geometry

Fitting each station to real cycle times and heights matters as much as the retarget, because a correct-looking worker on the wrong rhythm still reads as fake. Vendors rarely publish stance geometry, so the hard numbers below come from ergonomics regulators and vendor throughput claims.

| Station | Rate and cycle | Geometry and posture | Crew |
|---|---|---|---|
| Manual induction to cross-belt | **1,200–2,000 items/h per operator** ([Equinox](https://equinoxmhe.com/blog/induction-capacity-whitepaper/)), so about 1.8–3.0 s per parcel | Induction belts join at 30° or 45° ([Wikipedia](https://en.wikipedia.org/wiki/Cross_belt_sorter)); buffer "within reach" ([Equinox](https://equinoxmhe.com/blog/induction-capacity-whitepaper/)); operators face labels up "intuitively" ([BEUMER](https://www.beumergroup.com/knowledge/cep/how-to-sort-non-conveyable-and-irregular-parcels/)) | 1 per belt; 1 handler can serve 2 side-by-side inducts ([BEUMER](https://www.beumergroup.com/knowledge/cep/how-to-sort-non-conveyable-and-irregular-parcels/)) |
| Trailer unload to telescopic boom | **15–18 lifts/min** ([Waterloo CRE-MSD](https://uwaterloo.ca/centre-of-research-expertise-for-the-prevention-of-musculoskeletal-disorders/resources/fact-sheets-and-handouts/ergonomic-assessment-trailer-unloadload)), so about 3.3–4 s per lift | Hands at conveyor 103 cm, 40 cm reach; wall stacked floor to 180 cm; mostly 1–9 kg parcels ([Waterloo](https://uwaterloo.ca/centre-of-research-expertise-for-the-prevention-of-musculoskeletal-disorders/resources/fact-sheets-and-handouts/ergonomic-assessment-trailer-unloadload)); work the wall from the top ([BEUMER Parcel Picker](https://www.beumergroup.com/app/uploads/2019/05/BEUMER-Parcel-Picker.pdf)) | 1 per door, sometimes a helper |
| Bagging at chutes | Full-sack alerts on screens; sack nearest the operator swapped without moving the cart ([NPI](https://npisorters.com/chute-options/hds-chute/)) | Bags ≤25 kg are generally safe; 32 kg only for trained handlers ([HSE](https://www.hse.gov.uk/food/safety-hazards/roll-cages-wheeled-racks.htm)) | Not published |
| Roll-cage push | Walking pace, one cage at a time; 5+ transfers/min counts as repetitive ([HSE RAPP](https://hse.gov.uk/pubns/indg478.PDF)) | Handles about 1,000 mm; push, don't pull; cages 1,550–1,830 mm tall but most people can't see over 1,400 mm ([HSE](https://www.hse.gov.uk/food/safety-hazards/roll-cages-wheeled-racks.htm)) | 1 per cage |
| Bag tipping / singulation | Bulk parcels tipped into a hopper, then singulated and faced ([BEUMER](https://www.beumergroup.com/knowledge/cep/how-to-sort-non-conveyable-and-irregular-parcels/)) | Preferred handling zone 75–110 cm ([Waterloo](https://uwaterloo.ca/centre-of-research-expertise-for-the-prevention-of-musculoskeletal-disorders/resources/fact-sheets-and-handouts/ergonomic-assessment-trailer-unloadload)) | Not published |

These numbers tell you what each clip must contain. An inductor needs a short reach to a side buffer, a grab, a label-up turn and a place, about every 2.5 s with a small trunk turn each cycle. The turn angle is unmeasured, so judge it against reference footage. An unloader needs the whole height range in one cycle family: overhead reaches at the top tier, waist-height work in the middle and deep squats at the floor, all finishing at the 103 cm nose. Unloading at this rate is ergonomically extreme; the Waterloo study puts the lifting index at 18 lifts/min as effectively unbounded ([Waterloo](https://uwaterloo.ca/centre-of-research-expertise-for-the-prevention-of-musculoskeletal-disorders/resources/fact-sheets-and-handouts/ergonomic-assessment-trailer-unloadload)). So a realistic unloader slows over a take and pauses now and then, which is good for desync. HSE's MAC zones give a sanity check on posture. Green is hands between knee and elbow with the upper arms vertical. Red is at floor or head height, or twisted and bent at once ([HSE INDG383](https://www.hse.gov.uk/pubns/indg383.pdf)). A believable hub shows mostly green-zone handling with occasional amber bends. Manual induction also drifts over a shift into wide gaps and double feeds ([Realkey](https://www.rksort.com/why-induction-and-gap-control-decide-a-sorters-real-throughput/)), which justifies uneven cycle times. Local hubs such as Ninja Van Shah Alam run a "hybrid manual-automated mode" with handheld scanners ([MIDA](https://www.mida.gov.my/?p=77442)), so a scan beat belongs in some cycles.

For 20 workers, a split such as 6–8 inductors, 2–3 unloaders (one per open door), 4–5 at chutes and bagging, 2–3 cage pushers and 1–2 at singulation or supervising matches the crew rules above. That split is a design choice; no source gives a full hub crew mix. Spacing between inductors, aisle widths and boom nose height are unpublished, so set them from the 30°/45° induct belt pitch and check against reference video such as PhysicalAI-SmartSpaces.

## Desync and foot contact matter more than clip count

Perception studies say where to spend effort. **Three motions, desynchronised and spread evenly, gave "the illusion of a fully varied crowd"**, and one motion per 25 characters matched a fully unique crowd in a later study ([Vyas & O'Sullivan, summarising Pražák 2011 and Adili 2021](https://arxiv.org/html/2412.16151v1)). In a 12-avatar crowd, only the single-motion condition was detected above chance when repeats were set "out-of-step" ([Vyas & O'Sullivan](https://arxiv.org/html/2412.16151v1)). So the real zombie trigger is phase lock: everyone stepping, reaching and idling in sync from frame 0. Appearance clones are "far easier to detect than motion clones" ([McDonnell et al. 2008](https://research.gold.ac.uk/id/eprint/15203)). Rocketbox's many avatars already cover that, provided no two neighbours share a model. Two counterintuitive results argue against over-building. A bigger motion pool made viewers *perceive* more transitions even at the same real frequency, and more appearance variety made transitions easier to spot ([Gu, Yun & Deng 2010](https://graphics.cs.uh.edu/wp-content/uploads/papers/2010/VRST10.pdf)). Aim for about three good variants per frequent action, and blend only between similar motions. Three is a safety margin over the 1-in-25 finding, because 30–120 s takes expose loops.

Copy NVIDIA's design for task sequencing, since it is simple and documented. Isaac Sim's Replicator Agent drives people with a small command set (`GoTo`, `Idle`, `LookAround`, `Queue`). A weighted transition map picks the next command, with default ranges of Idle 2–6 s and LookAround 2–4 s. A `GoToBlend` joint filter layers an upper-body action over walking ([Isaac Sim Actor Control](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/action_and_event_data_generation/ext_replicator-agent/actor_control.html)). NVIDIA also admits its runtime avoidance is "best effort and not guaranteed" ([same](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/action_and_event_data_generation/ext_replicator-agent/actor_control.html)). With 20 workers, plan collision-free paths offline instead. Don't copy Unity PeopleSansPeople's "random frame of a random clip" trick: it works for stills but has no temporal coherence for video ([arXiv 2112.09290](https://arxiv.org/pdf/2112.09290v1)). Add Golaem's other levers per worker: a random start offset over 0–100% of the clip, a narrow speed ratio, and additive breathing or weight-shift layers with their own phase ([Golaem](https://help.autodesk.com/cloudhelp/ENU/GOLAEM-Maya/files/tutorials/animation-0/glm_adding-variety-your-characters-animation.html)). Social beats pay off too. Adding shoulder turns when characters pass improved perceived naturalness at almost no cost ([Hoyet et al.](https://history.siggraph.org/?p=102776)), and coherent group behaviour significantly reduced how noticeable transitions were ([Gu, Yun & Deng 2010](https://graphics.cs.uh.edu/wp-content/uploads/papers/2010/VRST10.pdf)). Scripted talking pairs at a chute, glances at a passing cage and a supervisor's look-around all add to this.

The CCTV viewpoint helps hide errors, but not foot errors. A top-down view hid transitions better than first-person (F = 32.91) ([Gu, Yun & Deng 2010](https://graphics.cs.uh.edu/wp-content/uploads/papers/2010/VRST10.pdf)), and at distance cheap representations become hard to tell from full meshes ([arXiv 2510.20558](https://arxiv.org/html/2510.20558)). That supports using Rocketbox's `midpoly` or `lowpoly` LODs ([Microsoft-Rocketbox](https://github.com/microsoft/Microsoft-Rocketbox)) for distant workers. Foot sliding is the exception: it is perceptible below about **21 mm** ([Pražák et al. 2011](https://diglib.eg.org/items/74844741-a900-4f91-886f-b89bf331cf98/full)). A 1920 px frame covering 20 m of floor works out to about 10 mm per pixel, so that threshold is about 2 px, visible on mid-frame workers. Fingers and faces are effectively invisible at CCTV scale; heads, shoulders and stepping are not. No perception study uses true surveillance viewpoints or 10–15 fps footage, so these priorities are reasoned from adjacent evidence.

## The ordered build plan

Each step depends on the one before it, so build in this order.

| # | Step | What to produce | Why it comes here |
|---|---|---|---|
| 1 | Licence gate | A `sources.csv` with licence, URL and credit line per file; exclude NC, Mixamo and the unverified MMH set | Excluded clips can't be removed once blended |
| 2 | Inspect Rocketbox | Bone-name dump, unit scale, bind-pose arm angle; a scripted swing-only T-pose; relaxed static fingers; fix transparent hair materials, which "look like glass sheets" in the Unity import without Microsoft's fix ([repo](https://github.com/microsoft/Microsoft-Rocketbox)) | Every later step assumes a known reference pose |
| 3 | Ingest sources | AndyData BVH and labels, 100STYLE trimmed by `Frame_Cuts.csv` (T-pose kept as reference), phone takes run through the offline FreeMoCap add-on, cleaned (bone lengths, 1€ filter), then exported to BVH | Noise must go before rotations are computed |
| 4 | Retarget to arrays | Per-clip numpy arrays of world rotations and scaled `Bip01` translation via the offset maths | Avoids local-axis bugs; keeps editing out of Blender's slow API |
| 5 | Per-clip clean-up | Quaternion continuity, per-clip ground calibration, foot-contact tags, event sidecar JSON | Editing needs reliable contacts and events |
| 6 | QA gate | Foot-skate per contact (target well under 21 mm), ground-penetration frame count, source vs target limb-direction error, orthographic overlay renders, side-by-side checks against Microsoft's 417 clips | Catches retarget errors before they multiply |
| 7 | Scene schedule | Station placement from the table above; a weighted Markov task chain per worker; offline collision-free paths | Fixes the times each clip must hit |
| 8 | Assemble per worker | Anchored PCHIP retime, displacement-curve root warp, best-frame inertialized transitions | Makes events land on scene times and places |
| 9 | Contact IK pass | Foot locks first, then hand IK as a ramped residual with the mocap pole, then parcel world-matrix baking | Repairs what warps and blends broke |
| 10 | Variation layer | Random start offsets, narrow speed ratios, breathing layer, LookAround and social beats, no shared avatar among neighbours | Removes phase lock, the main zombie trigger |
| 11 | Bake and render | Blender 5 slotted-action channelbags via bulk `foreach_set`; re-run the step 6 QA on final timelines | Final check that nothing reintroduced sliding |

## Conclusion

The research changes where effort should go. The intuitive plan, collecting more mocap, is the least valuable lever. Perception data says three good variants, played out of phase, beat a large library, and a larger pool can even make transitions more noticeable. The work that pays is mostly maintenance-free maths: one correct world-space retarget, leg-scaled root motion, inertialized joins, and a foot-lock pass held to a measurable target of about 2 cm. Each can be tested with a number before anyone watches a render. That suits a hackathon, because a QA gate after retargeting turns "looks off" arguments into a foot-skate figure in centimetres.

The open risks are clear. Rocketbox's actual bone list and bind pose, AndyData's label names and the missing manual-material-handling licence all need a quick hands-on check before code is written against them. Station spacing has no published source, so reference footage such as PhysicalAI-SmartSpaces should set it. The same footage gives the team a licence-clean way to judge "natural" from the camera angle that matters, instead of judging from the Blender viewport.
